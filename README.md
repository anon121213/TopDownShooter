# TopDownShooter

Краткое описание
---------------
Мультиплеерный top-down шутер на FishNet с реактивной моделью синхронизации (UniRx) и модульной архитектурой через VContainer Scopes. Проект построен по принципу server-authoritative логики, поддерживает пуллинг мобов и проджектайлов, локальную и удалённую инициализацию сущностей.

### Стек
`Unity` `FishNet` `VContainer` `UniRx` `UniTask` `Addressables`

Геймплей
----------
- Управление игроком (движение)
- Несколько типов врагов и простое ИИ-поведение
- Поддержка оружий, перезарядки и урона

Установка и запуск
------------------
1. Открыть ParrelSync и запустить клон проекта
2. Открыть NetowrkConfig, в нем выбрать client или Host подключение
3. Запустить Host игру, после запустить Client 

Дебагинг
--------
1. Открыть Dubug в Tool bar
2. Открыть нужные окна с дебагом network моделей

Управление (по умолчанию)
-------------------------
- Движение: WASD
- Смена оружия: Q

Структура проекта (пример)
-------------------------
- _Scripts/Infrastructure — Глобальные сервисы завязанные на архитектуре проекта
- _Scripts/Gameplay — Геймплейные скрипты
- _Data/ - Папка с конфигами


Примечания
---------
- Настройки врагов, игрока, оружия и прочего находятся в конфигах по пути _Data/

Описание
--------

Серверный подход был выбран сервер приприетарный но с локальным управлением объектом игрока.
Для симуляции плохо подключения можно использовать настройки в TransportManager
В проекте используется Scope архитектура, так можно проще менеджемнтитить local и remote сущностей и клиентов.
Так же в моделях вместо SyncVar синхранизация пропертей была выпонена при помощи Rpc методов, это увеличивает длинну кода но значительно упрощает менеджмент подписок и чтении модели благодаря UniRx
Всего есть 4 основых скопа: Root, NetworkRoomScope, GameScope, ArenaSceneScope

- RootScope отвечает за статические сервисы а так же работает как entrypoint проекта, там сетятся базовые значения
- NetworkRoomScope, в нем инициализируется сетевая состовляющая проекта а так же подключение сервера/клиентов
- GameScope отвечает за инициализацию игры, сейчас там просто смена сцены и warmup сервисов, при расширении проекта там должен регистрироваться GameMode service который будет овечать за настроки режима (спавн юнитов, респавн игроков и тд)
- ArenaSceneScope отвечает за сервисы и прочие сущности находящиеся на игровой сцене

Весь стейт игры находится в 2 моделях, NetorkRoomModel и ArenaSceneModel
- NetowrkRoomModel это основная модель проекта, содержит в себе весь сетевой стейт игры, ее может изменять только сервер, читают все (есть дебаг окно,смотри часть про дебагинг), нужна для чтения стейта игры (спавн юнитов, стейт слиента и тд)
- ArenaScneModel содержит в себе вьюшные части находящиеся на игровой сцене

Геймплейные скопы:
- LocalPlayerScope - скоп локального игрока, содежит инициализацию локального игрока
- RemotePlayerScope - скоп удаленных игроков, содержит инициализыцию remote вьюшек

- LocalMobScope - скоп инициализации локального моба (только сервер)

Геймплейная логика:

Игрок:
-----
При заходе клиента он получает NetowrkRoomModel, после чего начинается создание и инициализация локального игрока. Создается NetowrkPlayerView на сервере и отдается owner слиенту, клиент создает у себя LocalPlayerScope тогда как ремоуты создают Remote скопы, вместе со скопами так же сетится remote и local вьюшки игрока, это надо для оптимизации, так как remote игроку не обязательно иметь на себе компоненты нужные для его локальной логики. Внутри local скопа происходят все подписки жизненного цикла игрока. Так же каждый игрок имеет у себя собсвтвенную модель, там хранится весь стейт игрока, так же эта модель хранится в NetowrkRoomModel, кроме модели есть PlayerModelDataDTO, это dto с базовыми настройками игрка, она прокидывается между клиентами во время инициализации модели.

Мобы:
-----
В текущей версии имеется только LocalMobScope, в нем происходит вся инициализация моба, так же моб имеет в себе NetworkMobModel со всем стейтом моба (есть дебаг окно смотри часть про дебаг). Спавн моба происходит по заранее заданным точкам на сцене, MobSpawnerModel получает все эти точки на начинает спавн мобов с определенным интервалом заданным в точках спавна, так же в них указан тип моба для спавна, можно указывать более 1 моба. Повебение моба сделано через кастомый BehaviourTree, на данный момент есть 1 поведение - преслодование ближайшего игрока и дамаг при достижении определенного растояния. При смерти моб попадает в пул.

Проджектайлы:
-------------
В текущей версии scope для проджектайлов отсудствует, на данный момент есть базовый класс Projectile, его наследуют остальные проджектайлы, в нем во вьюшке находится логикуа движения и дамага проджектайла (должна быть пересена в сервис из локального скопа проджектайла). Спавнятся как с сервера так и с клиентов, для этого вызывается Spawn у ProjectileSpawner, он создает Dto в NetworkRoomModel и по ней уже на сервере спанится сам проджектайл. Есть 2 типа проджектайлов Grenade и Bullet, нужны для разных типов оружия у игрока.

Улутшения
---------
- Квантизация, на данный момент dto и прочие данные весят достаточно много, их все можно сжать для более меньшего объема трафика

- Батчинг, в NetworkRoomModel можно отправлять ивенты в определенным интервалом который будет задаваться в NetoworkConfig, для этого можно сделать очередь из EventData в которой будет лежать тип ивента для определения через какую rpc его прокинуть а так же сзжатая data которая в последствии будет расжиматься на клиентах/сервере при получении, таким образом количество ивентом будет меньшее и мы не потеряем порядок вызовов

- Rollback, в NetworkRoomModel можно хранить стейт за последние 60 кадров, как пример, в момент выстрела делать Predicted Spawn пули на клиенте, так же отправлять на сервер вместе с ивентом кадр в которм был вызван ивент и проверять возможено ли было попадание (нужно дабы избажать проблем с пингом).

- Добавить Remote скоп и NetworkView для Мобов, сделать анологично с тем как сделан игрок, это позволит немного облегчить нагрузку на клиентов и сделать более удобным хэндл самих мобов 

- Добавить скопы для проджектайлов, сделать анологично тому что сделано с плеером, в таком случае пропадет проблема с запоздалым спавном проджектайлов и так же ошибка что ngo не был заресечен

- Добавить prediction для проджектайлов, мобов и игроков

- Избавится от FinObjectOfType для NetworkRoomModel на клиентах а так же от подписки на поиск arena scene scope у network view игроков, надо сделать смену сцены мануальной и только после спавна netowrkRoomModel продолжать инициализацию

- Написать сервис для отправки любых ивентов и смены состояния netowrk моделей из вне монобехов. Решит прлблемы с FinObjectOfType а так же необходипостью спавна всех моделей как networkobject (решено в моем netcode framework: https://github.com/anon121213/NetCodeFramework)
